2-1. 座標と形の決め方

  • ローカル座標は x=板の幅、y=板の厚さ、z=高さ。板は y ∈ [-thickness/2, +thickness/2]、z ∈ [-height/2, +height/2]
  • 板の輪郭は wallSignFacePoints(params)（幅×高さの4隅を丸めた多角形）。表裏・側面・線画・メッシュ・外接範囲で共有
  • ベベルは表裏の輪郭の4隅（幅×高さ）へ付く。bevelMax = min(width, height) * 0.45 - 0.001
  • 取付金具は板の左側面（-x）から横へまっすぐ伸びる単純な直方体（z軸回りに反時計回り90度回した面が取付面）
    • x0 = -width/2 - bracketLength、x1 = -width/2
    • 太さは y ∈ [-thickness/2, +thickness/2] に収め、板の表裏からはみ出させない
    • 高さ位置 z = height*(i+1)/(count+1) - height/2（中央から上下へ等間隔）
  • 既定値：rot: 0、wallSignShape: "beveled"、wallSignBevelOffset: 0.18、wallSignBevelSegments: 4、金具3本・長さ0.36

4-5. 屋根の板厚（2026-10-29）

外側の断面  outerPath = [ (-halfSpan, lowZ), (0, h), (+halfSpan, lowZ) ]   ← 切妻
内向き法線  n = 接線を −90°回したもの
内側の断面  innerPath = offsetPolyline2D(outerPath, thickness)             ← マイター交点方式
断面        cross = outerPath + reverse(innerPath)  → 棟方向へ ±half 押し出す
  • どの面でも内側は外側から法線距離 thickness だけ離れるので、勾配・軒の出・棟の高さを
    変えても板厚は一定
  • 折れ点は隣り合う2直線の交点（マイター）で取るため、棟の角も途切れない
  • 両端（軒先）は鉛直に切る（垂木の小口と同じ）。下げ量は t / cosθ。
    法線方向へずらすだけだと軒先が棟方向へ伸びて屋根の中心がずれるため、端だけ垂直に切り落としている。
    鉛直に切っても斜面上の垂距離は t のまま（検算済み）
  • 「下の建物に合わせる」はこの下げ量 t / cosθ を見て持ち上げるので、軒が建物へめり込まない
  • 線画（roofSlabLines）と面メッシュ（exportSurfaceTriangles）が 同じ roofSlab() を使うので、
    面表示と線が食い違わない

4-6. 窓の分割数と大きさ（2026-10-29）

窓グリッドを選ぶと左パネルに 行・列・窓の幅・窓の高さ が出ます。
画面上では 左上の窓の右辺（幅）と上辺（高さ） に水色の菱形ハンドルが出るので、直接ドラッグもできます。 

cellW = (wallW − 余白×2 − 横間隔×(列−1)) / 列
winW  = min(cellW, 窓の幅)          ← 指定が無い(0)ときは cellW いっぱい
padX  = (cellW − winW) / 2          ← 余りは左右へ均等（＝窓のまわりの壁が増える）
  • 窓を小さくすると、四方の壁が均等に増える（中央寄せ）ので見た目が崩れない
  • 指定値がセルより大きいときは セル寸法で自動的に頭打ち（窓どうしが重ならない）
  • 行・列は 0〜20、窓の幅・高さは 0（自動）以上

4-6b. 屋根の断面キャップ（2026-10-29）

屋根の両端（断面）の面は、以前は「重心から各頂点への扇」で三角形に割っていました。
屋根の断面は凹んだ形（山形＋内側の山形）なので、扇の三角形が断面の外へはみ出し、
「塗らなくてよい所まで塗られる」状態になっていました。
現在は 耳切り法（polygonEarClip） で、必ず断面の内側だけを三角形に分けます。 

耳切り（ear clipping）
  1. 頂点の並びの向き（時計／反時計）を面積の符号で調べる
  2. 「となり合う3点が作る三角形」が凹みを含まず、他の頂点を巻き込まない頂点を1つ選ぶ
  3. その三角形を確定して頂点を1つ減らす → 残り3点で終わり

検算（幅 4.2・奥行き 3.2・棟高 1.35・板厚 0.2 の切妻屋根）:
断面積 0.5362 ＝ キャップ三角形の総面積 0.5362（片側 0.2681）。
polygonEarClip が無い環境では自動的に昔の扇へ戻ります。

  • 関節を回すと pose は custom になり、プリセット（直立・歩行・しゃがみ・着席）は選択解除。
    プリセットを押すと関節角度は 0 に戻ります
  • 同じ値は左パネルの 腰の回転／首の回転／左右の股関節／左右の膝（°）でも編集でき、
    「ポーズを微調整」で反映します
  • 角度の計算は asset.js の personPose() 1か所。線画・面メッシュ・ハンドル位置が同じ骨格を
    使うので、回しても線と面がずれません

5B. オブジェクトロック／カメラロック（2026-10-30 追加）

「もう動かしたくないもの」と「もう視点を変えたくない」を、それぞれ固定できるようにした。
2つは別物で、片方だけ使うことも両方同時に使うこともできる。

5B-1. オブジェクトロック（図形を固定）

項目内容
入口上部バー ロック／シーン一覧の各行の鍵アイコン／選択をロック・全ロック解除／⌘/Ctrl + L
保存図形の定義に locked: true が入るので、JSON保存・読み込み・自動保存でそのまま残る（保存形式の変更なし）
ロック中にできないこと選択（クリック・箱選択・全選択）、ギズモでの移動／拡大／回転、数値パネル、整列、結合・グループ化、削除（Xキー・選択中を削除・全消去）
ロック中にできること表示／非表示（一覧の目のアイコン）、ロック解除だけは一覧の鍵・バー・⌘/Ctrl+L からいつでも可能
連動建物に接着した子（テント・看板）は親と一緒にロック。グループは全員そろってロック
画面表示ロック中の図形の真上に小さな鍵。一覧の行は鍵アイコンが青くなり、チェックボックスが押せなくなる

実装の要点：判定を1か所に集めている。ロック中かを決めるのは obLocked(o)（engine-core.js）だけで、

  • setOb() … ロック中は locked／visible 以外の変更を捨てる（ギズモも数値パネルも整列も、すべてここを通る）
  • pickOb()／setSelection()／normalizeSelection() … ロック中は選択しない
  • deleteSelectedObjects()／finishBoxSelection()／全消去 … ロック中は消さない・選ばない

という4か所だけ。ギズモや各アセットのハンドルを個別に直す必要がないので、
今後アセットを増やしても自動的にロックが効く。

5B-2. カメラロック（視点を固定）

項目内容
入口上部バー カメラ固定／L キー
固定するものカメラ位置（cx/cz/ch）・向き（yaw/pitch/roll）・レンズ・魚眼画角・画面上のズームと移動（Z/ox/oy）
固定しないものオブジェクトの編集（移動・拡大・回転はそのまま）、表示切り替え（面ON/OFF・補助線・グリッド）、3D⇄前／横／上の切り替え
画面表示画面左下に「カメラ固定」ラベル、ボタンは黄色く点灯
保存保存しない（ファイルを開いたら解除される）。開いた直後に視点が戻せない、という事故を避けるため

実装の要点：視点を動かす入口は7種類以上ある（3Dドラッグ・パン・ホイール・ピンチ・矢印キー・
左パネルのスライダー／数値入力・標準ビュー・間取りのカメラ操作）。全部に個別のガードを書くと
必ず抜けるので、2段構えにした。

  1. setP() と左パネルの入力で書き込みを拒否（その場でつまみも元へ戻す）
  2. それでも変わった場合に備え、render() の先頭で enforceCameraLock() が記録した値へ戻す

5N. 生成面が効かないアセット（2026-11-01 追加）

5N-1. 症状

5N-2. 原因（3つ）

  1. 積層建物・壁付け看板が k を1に固定していた

  2. 積層建物の線画が customPt()（自作の式）で描かれていた

  3. 生成面は「新しく追加するアセット」にしか効かなかった
    すでに置いてあるアセットには何も起きないので、変化が無いように見えていた。

  • 積層建物（3種）・壁付けベランダ・壁付け看板の k 固定を廃止し、共通設定に従う。
  • customPt を L2W へ委譲（const customPt = (o, x, y, z) => L2W(o, x, y, z);）。
    k=1, rot=0 では従来と完全に同じ値なので既存データの見た目は変わらない。

5O. 画面の回転を「どの向きにも」できるように（2026-11-01 追加）

5O-1. 症状

5O-2. 仕組み

  • オブジェクトに rotX（左右＝ワールドX軸）と rotZ（手前奥＝ワールドZ軸）を追加。

5P. 壁付きベランダの壁の厚さを画面上で変える（2026-11-01 追加）

5P-1. 症状

壁付きベランダの腰壁の厚さは左パネルの数値（balconyRailThickness）でしか変えられず、
3Dビュー・間取りビューのどちらでも画面上で掴めなかった。床の厚さも同じ。

5P-2. 仕組み

  • balconyGeometry(o)（engine-tools.js）に寸法を集約。asset.js の linesBalcony も
    この関数を呼ぶので、線画・面・数値パネル・ハンドルが必ず同じ数を見る。
    • thickness = clamp(balconyThickness || 0.14, 0.035, min(w,d)*0.35) … 床と壁で共通
    • railH = clamp(balconyRailHeight || h - thickness, 0.12, h - 0.01)
    • h = thickness + railH（厚さを増やすと全体の高さも伸びる）
  • balconyGizmo(o) が作るハンドルは1つ（2026-11-01：床と壁で厚さを分けない指示）。
    • balcony-thickness（壁の厚さ・#ff9f68）＝前面腰壁の外側面に置く四角。
      外側へドラッグすると厚くなる。床スラブも同じ値で厚くなる。
  • specialGizmo() に balcony 分岐、drawSpecialGizmo に「ラベル付きの四角＋破線」の描画分岐。
  • beginGizmo の kind 一覧と dragEdit の patch に2種を追加。床の厚さは h も同時に更新
    （h = 新しい floorT + railH）。数値パネルの applyBalconyProp と同じ扱い。
  • 間取り（正面・横・上）でも同じハンドルを floorPlanEditHandles に inner:true で出し、
    ドラッグの patch 分岐も同じ値を書く＝ビューによる編集能力の差を作らない。

5P-3. つまずいた所（重要）

専用ハンドルは hitGizmo() の special 分岐に登録しないと掴めない。
登録が無いと、掴んでも「ゴミ箱判定」に落ちて値が変わらない（ハンドルは表示されるのに
ドラッグしても無反応、という症状になる）。wallSign / windowGrid と同じ型で
nearestHandleOf(Object.values(special.handles), p, R) → handleOrFace を通す。

5P-5. ドラッグの向きについて

ハンドルのドラッグ量は「ハンドルの基準線が画面で向いている方向」へ投影している。
そのため画面で線が縦に見えるビューでは縦にドラッグする（横に振っても値は動かない）。
これは壁・看板・窓グリッドなど従来のハンドルと同じ規則で、ビューごとの例外は作っていない。

5T. 円・円柱・球・丸椅子の線画と半径ハンドル（2026-11-02 追加）

5T-1. 何が起きていたか（原因）

genShape()（engine-core.js）のプリミティブ（rect / circ / box / cyl /
triPrism / triPyramid）は、面内の座標を q() で直接組み立てていました。
q() は l2wRaw() 相当の式を自前で書いていたため、L2W() が掛けている
オブジェクトの傾き（rotX / rotZ）が掛かりません。

5V. 結合オブジェクトの回転（2026-11-02 追加・同日 最終形）

「結合したオブジェクトを回すと位置がずれる／動く」の修正。

5V-1. 原因（3つ重なっていた）

① 軸を毎回作り直していた。
回転の軸を「そのときの外接箱の中心」から計算し直していた。箱は回すと形が変わるので
中心も動く（30°ごとに 0.16〜0.68 m）。そのため回すたびに別の点を中心に回っていた。

② 子パーツの off を回していなかった。
パーツの位置は ca/cb（面の中の座標）と off（ワールド方向の平行移動）に分かれている。
位置だけ回して off を据え置くと、その分だけワールド軸のまま取り残される。
実データの off = [5.15, 0, -0.55] を −45° 回すと 3.96 m ずれていた。

③ 角度の決まりが2種類あって、形だけ逆に回っていた（これが一番大きい）。
図形の rot（面の中の回転）と、回転で使う中心移動の式が逆向きだった。

計算式向き
形の rot（l2wRaw）x' = x·cos − y·sin, y' = x·sin + y·cos＋で反時計
中心・off の移動（旧 rotateCompoundBy）x' = x·cos + z·sin, z' = −x·sin + z·cos＋で時計

そのため「中心は ＋15° 回るのに、形は −15° 回る」＝ 形が二重に回って 30° ずれる。
パーツの中心どうしの距離は変わらない（＝剛体に見える）ので、中心だけで測ると気づけない。
角の点まで測って初めて出た（中心だけで確認していたのが、直ったと誤認した原因）。

④（おまけ）接着しているパーツ。 結合した横壁看板は、外に残っている親の壁へ
吸い戻されていた（syncAttachedPart）。

5X. 面ONのときの線画を根本から直す（2026-11-02 追加）

「面ONにすると、描かなくていい線まで描いている」という指摘への対応。
原因は隠線除去（深度バッファ）の判定にあり、線のデータ自体ではなかった。
データ側は genShape の段階で「同じ稜線を2本持っている」ぶんを印（.dup）で間引いている。

5X-1. 何が起きていたか

症状原因
面と面が接する稜線（壁の下端と台の上面など）が点線状に欠ける線の奥行きと面の奥行きが数mm食い違い、画素ごとに判定が反転していた
面を真横から見ている所で線が点線になる1画素の中でも面の奥行きが大きく変わるため、中心1画素の比較では足りなかった
自分の面の上に乗っている稜線が消える深度バッファは「いちばん手前の面」しか持たず、線が自分の面の数mm奥と判定されていた
遮蔽物との境目で線が数十px ずれて切れる区間の刻みがワールド長 10cm 固定だった（拡大するほど誤差が目立つ）

5X-2. 直したこと（engine-render.js）

  1. 面の持ち主（ID）を持つようにした … buildExportDepth() が深度と一緒に
    depthOwner（画素ごとのオブジェクト番号）を書く。線の画素の面が「その線の持ち主」で
    奥行きがほぼ同じなら、その線は自分の面の稜線なので描く（SELF_EDGE_EPS = 0.02）。
    Blender の線画アドオン（FreePencil2）が使っている「面IDごとの可視判定」と同じ考え方。
  2. 接している線は近くの画素も見る … nearVisible() が 3×3 画素の奥行きの
    ばらつきを見て、真横に近い面ほど許容を広げる（上限 25cm）。
    これで「点線」「継ぎ目で切れる」が消えた。
  3. 区間の刻みを画面上の長さにした … 2点の投影結果から内部を補間する
    （直線は透視投影でも画面上は直線、奥行きは 1/奥行き が1次）。
    刻みは 6px（ドラッグ中は 20px）。遮蔽物との境目で線が切れる位置が合う。
    さらに「区間全体が同じ状態か」を粗く先に調べ、境界が無い区間は刻まない。
  4. 投影は点ごとに1回 … 以前は区間の両端でもう一度投影していた（同じ点を2回計算）。

  • lineLayer() の戻り値は毎回同じキャンバス（LC）。 隠線あり／なしの画素数を
    比べるときに両方を変数へ取ると、両方が同じ（後から描いた方の）内容になる。

5Y. 画面上のラベルと回転ギズモの見え方（2026-11-01 追加）

5Y-1. ラベルは「白いチップ＋濃い文字」に統一（gzLabel()）

背景が白い用紙になったあとも、ハンドルの名前と値はハンドルと同じ明るい色
（#fff0b0 / #ffd0a8 / #d8fff0 など）で描いていたため、白背景ではほぼ読めなかった。
engine-gizmo.js の gzLabel(c, text, x, y, color, font) に一本化し、次の見た目にした。

  • 白い角丸チップ（rgba(255,255,255,.95)＋薄い影）・文字は濃い色 #1f2933
  • ハンドルの色はチップの枠と左端の細い帯で示す（gzLabelTone() で明るい色を暗くしてから使う）
  • font は画面上のピクセル数。内部で Z で割るので、ズームしても大きさが変わらない

同じフレームに置いたチップの矩形は gzLabelRects に貯め、重なるときは上へ逃がす
（16回まで上・16回まで下・最後は右）。屋台の「屋根の高さ」と「壁の厚さ」のように
近い位置に並ぶラベルが重なって読めなくなっていたのを解消した。
矩形は c.getTransform() でデバイスpxに直してから比較する。呼び出し側によっては
描画変換がズーム付き（Z, ox, oy）だったり素のpxだったりするため、そのままの座標で
比べると別の変換どうしのラベルを見落とす（間取りの「上端」と専用ハンドルがこれで重なっていた）。
位置の記憶は render() の先頭で gzLabelReset() が捨てる（1フレーム分だけ有効）。

5Y-2. 回転ギズモの輪の大きさをそろえる

以前は上下リング（g.ring）だけ max(ra, rb) * 1.4、左右・手前奥の傾きリングは
対角 * 0.42 + 0.2 と別々の式で、同じギズモなのに輪の大きさが違っていた。
外周の輪（画面に平行な輪）も最大の輪の1.12倍で、いちばん目立つ円になっていた。

  • 3本とも ringR = clamp(対角 * 0.5, 0.45, 60) の同じ半径にした
  • 外周の輪は最大の輪の 1.03倍（ほぼ同じ大きさ）
  • 中心の輪・回転中の破線は白背景で見えなかったので灰色（#5a6b78 / #7d8b96）にした
  • 上下リングは形の底面（z0）に置いたまま。中心の高さに置くと、左右・手前奥の
    白い面ハンドル（±ra / ±rb）と画面上で重なり、回転と寸法ハンドルを取り違える
    （実際に hitGizmo が面を返すようになり、リングを掴めなくなった）

5Y-3. 間取りビュー（前・横・上）でも回転ギズモを掴める

e.__cityFloorPlanPreempt = true を立て、engine-input.js の通常処理を止めていた。

// asset.js — 弧の上の点には印だけ付ける（描くかどうかは描画側が決める）
function beveledEdgeMark(index, offset, segments, group = 0) {
    const b = Math.abs(Number(offset) || 0),
        seg = beveledBoxSegments(segments),
        n = seg + 1,
        i = ((index % n) + n) % n;
    if (b <= 0.000001 || seg <= 1) return null;   // ベベル無し・平らな面取り1枚は普通の稜線
    return { key: group + ":" + Math.round((index - i) / n), apex: i === Math.round((n - 1) / 2) };
}
// 呼び出し側：line.seam = mark.key; line.seamApex = mark.apex;

5Z-2. ドラッグ中は「動いた1台ぶん」だけ深度を作り直す（dirty rect）

面ONの隠線は、面の奥行きを1枚の深度バッファへ塗ってから線を判定している。
以前はオブジェクトが1台でも動くと全面を作り直していた（実測 11〜21ms/フレーム）。

buildExportDepth() を次の2段構えに変えた。

  1. 静止分のキャッシュ：動いている1台を除いた面の奥行きを
    depthStatic に作る（キーはカメラ・設定・その他のオブジェクトの中身）。
  2. 毎フレーム：前フレームで動いていた1台が塗った行を消す → 静止分を
    Float32Array.set() で貼る → 動いた1台の面だけを塗る。

「どの1台が動いたか」は、フレームごとにオブジェクトの JSON を比べて
1台だけ変わったときを検出して決める（複数選択の一括変形・追加/削除・カメラ移動は
従来どおり全面計算）。塗る本体は rasterizeDepthInto() に切り出して共用する。

実測（手すり×6＋ベベル階層建物×4＝10台・952本・3,928三角形、1400×900）:

ドラッグ開始の1フレームだけ＋約 30ms（静止分キャッシュの作成）

（window.__noDirtyDepth = true で従来経路に切り替えられる）。

5Z-2b. dirty rect の不具合修正（2026-11-02）

症状：オブジェクトを1台だけ置いて回転させると、面ONの線が大量に消えた
（ベベル直方体 rot35 で 4,493 → 2,673 画素）。window.__noDirtyDepth = true にすると
5,305 画素に戻ることから、dirty rect 経路が原因と判明。

原因：消す行の範囲を
Math.min(depthMovingUsedY0, depthStatic.y0) で決めていた。シーンに1台しか無いと
「静止分」は空（y0 = Infinity）になり、Math.min(...) が Infinity になって
前フレームの奥行きを1行も消していなかった。残った奥行きが手前にあるため、
線が「別の面に隠れている」と誤判定されて消えていた。

修正：有限な値だけを使って min/max を取る（空の側は無視する）。
1台だけの場面でも、前フレームで動いた1台が塗った行が正しく消える。

確認：1台／2台の両方で、rot 0→25→50→75 と動かしながら
dirty 経路と全面再計算の描画を画素比較 → 全ケース diff 0。

5Z-6. 面の層・線の層を作り直さない（2026-11-02 追加）

drawObjectSurfaces() と lineLayer() は毎回すべて描き直していたが、
カメラ・用紙・設定・オブジェクト・選択が前回と同じなら、前回の層をそのまま使うようにした。

    キーは W,H,Z,ox,oy ＋ JSON.stringify(P) ＋ 見えているオブジェクトの JSON.stringify ＋ sel
    （線の層は bin と hidden・書き出し変換 tf も含む）。1フレームあたり 0.3〜0.5ms。
  • 逃げ道：window.__noSurfCache / window.__noLineCache。
  • 編集中の線（withCur）が乗るときは、線の層は内容が毎フレーム変わるのでキャッシュしない。
  • 層が2枚以上（不透明度の違うオブジェクトが混在）のときは、面の層はキャッシュしない
    （オフスクリーンは1枚を使い回しているため）。
